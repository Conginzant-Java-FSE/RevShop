                               REVSHOP PROJECT

1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
RevShop is a comprehensive, full-stack, enterprise-grade e-commerce application 
designed to facilitate a seamless online shopping experience. It connects three 
primary user groups: Buyers, Sellers, and Shippers. 

The primary objective of RevShop is to provide a robust, scalable, and secure 
platform for multi-vendor product listings, real-time inventory management, 
shopping cart processing, secure financial transactions, order lifecycle 
tracking, and reliable localized delivery.

The application leverages a modern technology stack, decoupling the frontend 
presentation layer from the backend business logic and data access layer. 
The backend is a RESTful API powered by Java 21 and the Spring Boot 3 
framework. The frontend is a Single Page Application (SPA) driven by Angular 21, 
TypeScript, and RxJS for reactive state management. The data layer is backed by 
a relational MySQL database, accessed via Spring Data JPA and Hibernate ORM.

This document serves as the comprehensive architectural and functional breakdown 
of the RevShop platform, detailing the technologies utilized, the implemented 
features, the relational database structure, and the automated testing protocols.


2. ARCHITECTURAL DESIGN
--------------------------------------------------------------------------------
2.1 Client-Server Model
RevShop employs a strict Client-Server decoupled architecture. The frontend 
(Angular) handles all user-facing interactions, DOM manipulation, state 
management, and dynamic rendering. It communicates asynchronously with the 
backend (Spring Boot) via HTTP REST APIs, exclusively sending and receiving 
JSON payloads payload formats.

2.2 Layered Backend Architecture
The backend enforces a strict separation of concerns through the following layers:
- Controllers (@RestController): Handles incoming HTTP requests, extracts request
  bodies or parameters, invokes the appropriate Service layer methodology, and 
  returns the serialized HTTP response (ResponseEntity) with correct status codes.
- Services (@Service): Encapsulates the core business logic. Contains algorithms
  for cart computations, order processing, wallet deductions, password hashing, 
  and interactions with third-party SDKs (Twilio, Razorpay).
- Data Access Objects / Repositories (@Repository): Utilizes Spring Data JPA 
  interfaces to abstract away low-level SQL queries. Handles CRUD operations 
  directly against the MySQL database.
- Entities / Models (@Entity): POJOs mapped directly to MySQL database tables 
  using Hibernate annotations.
- Data Transfer Objects (DTOs): Flat structures used strictly to transfer data 
  between the client and server without exposing internal domain logic or 
  circular object references.

2.3 Security Architecture (JWT + Spring Security)
RevShop is completely stateless on the server side to ensure high scalability.
It implements a token-based authentication mechanism using JSON Web Tokens (JWT).
Upon successful login, the server generates a cryptographically signed JWT 
containing the user's ID, role, and expiration timestamp. The client stores this 
token (typically in LocalStorage or HttpOnly cookies) and appends it to the 
Authorization header of all subsequent secured requests. Spring Security 
intercepts these requests, validates the JWT signature, and enforces Role-Based 
Access Control (RBAC) rules.


3. TECHNOLOGY STACK
--------------------------------------------------------------------------------
3.1 Backend Stack
- Java: Version 21 (LTS) providing modern language features like records.
- Spring Boot: Version 3.4.x, offering auto-configuration and rapid development.
- Spring Web: To build the RESTful API endpoints.
- Spring Data JPA: Abstraction over JDBC and Hibernate for data access.
- Hibernate Core: Object-Relational Mapping (ORM) framework.
- Spring Security: For enterprise-level authentication and authorization.
- JJWT (io.jsonwebtoken): For creating, signing, and parsing JSON Web Tokens.
- Spring Boot Starter Mail: For asynchronous email delivery routines.
- MySQL Connector/J: The official JDBC driver for MySQL.

3.2 Frontend Stack
- Angular: Version 21, providing a component-based architecture for the SPA.
- TypeScript: Strongly-typed superset of JavaScript ensuring frontend reliability.
- RxJS (Reactive Extensions for JavaScript): For handling asynchronous API calls,
  managing application state, and subscribing to data streams.
- Angular CLI: Tooling for building, scaffolding, and testing the application.
- HTML5 & CSS3: Semantic markup and flexbox/grid layouts for responsiveness.

3.3 Third-Party Integrations & APIs
- Razorpay Java SDK: Integrated payment gateway to securely process credit card, 
  debit card, and UPI transactions. Provides automated webhook callbacks for 
  payment success/failure validation.
- Twilio Java SDK: Integrated cloud communications platform used to send SMS 
  messages containing One-Time Passwords (OTPs) for enhanced user verification 
  and critical real-time alerts.

3.4 Testing & Quality Assurance
- Backend Testing: JUnit 5 (Jupiter) and Mockito for isolated unit tests and 
  integration tests evaluating service logic and endpoint responses.
- Frontend Testing: Karma as the test runner and Jasmine as the assertion 
  framework to test Angular components, services, and pipes.
- Code Coverage Tooling: JaCoCo (Java Code Coverage) Maven plugin utilized to 
  enforce branching and line coverage thresholds.
- SonarQube: Used in CI/CD pipelines to analyze code complexity, enforce styling 
  rules, and detect potential security vulnerabilities or "code smells."
- DB Testing: H2 In-Memory Database utilized during integration tests to prevent
  polluting the production/development MySQL schemas.

3.5 API Documentation
- SpringDoc OpenAPI 3 (Swagger UI): Auto-generates interactive API documentation
  accessible via a browser, allowing frontend developers to test endpoints, 
  inspect required JSON payloads, and view HTTP status definitions.


4. USER ROLES AND PERMISSIONS (RBAC)
--------------------------------------------------------------------------------
The application meticulously restricts endpoint access based on three distinct 
user roles:

4.1 Buyer Role
- Can browse categories, search for products, and view detailed product pages.
- Can add, update quantities, and remove items from their dedicated Shopping Cart.
- Can apply discount coupons and promotional codes at checkout.
- Can execute secure checkout processes using Razorpay or their Digital Wallet.
- Can track chronological order history and view real-time shipping updates.
- Can leave text-based reviews and numerical ratings on purchased products.
- Can manage personal profile data, delivery addresses, and wallet balances.
- Can permanently delete or temporarily deactivate their account.

4.2 Seller Role
- Possesses a dedicated "Seller Dashboard" to oversee their digital storefront.
- Can create, read, update, and delete (CRUD) their specific product listings.
- Can manage product inventory levels (stock counts).
- Can view aggregate sales data, revenue metrics, and pending orders.
- Can update order statuses (e.g., from "Pending" to "Processing").

4.3 Shipper (Delivery) Role
- Possesses a specialized "Shipper Portal" to manage logistics.
- Can view assigned delivery payloads grouped by geographic areas.
- Can update real-time Tracking Details (e.g., "Dispatched", "In Transit").
- Can trigger Twilio SMS notifications to the buyer upon status changes.
- Can mark an order as "Delivered" requiring buyer OTP confirmation (if enabled).


5. DOMAIN MODEL & DATABASE SCHEMA
--------------------------------------------------------------------------------
The backend is supported by a robust, 20+ table relational database constructed 
in MySQL. Key entities and their relationships include:

- User Entity: The foundational account table storing email, hashed passwords, 
  and role discriminators (Buyer, Seller, Shipper).
- Buyer, Seller, Shipper Entities: Subtypes extending the User table with 
  role-specific attributes (e.g., Seller company name, Shipper vehicle ID).
- Product Entity: Stores product metadata (name, description, price, stock, 
  image URLs). Has a Many-To-One relationship with the Seller entity and a 
  Many-To-One relationship with the Category entity.
- Category Entity: Hierarchical grouping for products (e.g., Electronics, Home).
- Address Entity: Stores localized shipping and billing details, linked to Users.
- Cart Entity: Maps uniquely One-To-One with a Buyer.
- CartItem Entity: Maps the Many-To-Many relationship between Carts and Products,
  storing the quantity of a specific product requested.
- Orders Entity: The immutable historical record of a checkout event, capturing 
  the total cost, timestamp, linked Buyer, and applied Coupons.
- OrderItems Entity: Immutable snapshot of CartItems at the moment of checkout, 
  ensuring that if a Seller changes a product price later, the historical order 
  receipt remains accurate.
- Payments Entity: Tracks Razerpay transaction IDs, payment methods, status 
  (SUCCESS, FAILED, PENDING), and links to the specific Order.
- TrackingDetails Entity: A chronological log mapping to an Order, updated by 
  the Shipper to reflect delivery progress.
- Review Entity: Links a Buyer to a Product with a numerical rating (1-5) and 
  text feedback. Enforces uniqueness so a buyer can only review a product once.
- Wallet & WalletTransaction Entities: Manages the digital currency ledger for 
  a Buyer, logging all credits (top-ups) and debits (purchases).
- Coupon Entity: Stores discount logic (percentage or flat rate), expiration 
  dates, and minimum purchase requirements.
- Notification Entity: System-generated alerts mapped to a User.
- PasswordResetToken Entity: Temporary, time-sensitive cryptographic hashes 
  used for secure account recovery workflows.


6. DETAILED FEATURE BREAKDOWN - BACKEND (SPRING BOOT)
--------------------------------------------------------------------------------
6.1 Cart and CartItem Management
The core e-commerce engine relies on highly transactional cart endpoints.
- Add to Cart: The backend verifies product existence and stock availability 
  before creating or updating a CartItem. 
- Update Quantity: Validates that the requested quantity does not exceed Seller 
  inventory. Uses JPA pessimistic locking or transactional isolation to prevent 
  race conditions if two buyers attempt to buy the last item simultaneously.
- Clear Cart: Efficient bulk deletion of CartItems upon successful checkout.

6.2 Search, Filtering, and Pagination
The ProductController exposes complex search algorithms utilizing JPA native 
queries or custom @Query HQL implementations. Data can be filtered dynamically 
by category, minimum/maximum price boundaries, and average review ratings. 
Pagination is implemented using Spring Data's Pageable interface, returning 
chunked data to the client to reduce payload size and database load.

6.3 Payment Processing (Razorpay Integration)
The standard checkout flow requires creating an "Order" object within the 
Razorpay system first. The backend initiates an API call to Razorpay, receives 
a dynamic Razorpay Order ID, and passes it to the Angular frontend. The client 
then renders the Razorpay payment modal. Upon user payment, Razorpay redirects 
back to the application with a cryptographic signature. The backend securely 
validates this SHA256 HMAC signature against the server's private secret key 
before confirming the purchase and deducting actual inventory.

6.4 Promotional Coupons and Discounts
Coupons possess specific state rules: they may be tied to a specific product, 
a specific category, or globally applied. They possess chronological expiration 
validations. The backend computes the final cart total by dynamically applying 
these logical parameters before checkout execution.

6.5 Reviews and Dynamic Rating Aggregation
Buyers can submit reviews only for products they have historically purchased 
and received. The backend calculates aggregate product ratings asynchronously 
or dynamically via database triggers, updating the master Product entity's 
average rating to optimize read-heavy frontend catalog views.

6.6 User Wallet Architecture
The platform features an internal ledger system. Buyers can deposit real fiat 
currency into an immutable ledger table. The system calculates their current 
balance using mathematical SUM queries rather than a single mutable balance 
column, guaranteeing atomic accuracy and preventing lost update anomalies 
during concurrent transactions.

6.7 Account Lifecycle (Deactivation & Deletion)
Users have full GDPR-compliant control over their data. "Deactivation" is 
handled via a fast boolean toggle column (isActive = false), instantly locking 
them out while retaining data. "Deletion" initiates a complex cascading routine,
removing sensitive personal identifiable information (PII) while anonymizing 
essential financial records (like old Orders) to preserve the Seller's holistic 
revenue metrics.


7. DETAILED FEATURE BREAKDOWN - FRONTEND (ANGULAR)
--------------------------------------------------------------------------------
7.1 Component Modularity
Angular UI is strictly compartmentalized. Reusable components like "ProductCard",
"StarRating", and "CustomToast" are distributed throughout the views. The 
AppModule is segmented into featured modules (AuthModule, BuyerModule, 
SellerModule) leveraging Angular's Lazy Loading mechanism to aggressively shrink 
initial vendor bundle sizes and improve Time-To-Interactive (TTI) performance.

7.2 Reactive State Management with RxJS
Cart item counters in the navigation bar and total price calculations on the 
checkout page update instantaneously via RxJS BehaviorSubjects. When a user 
adds an item, the CartService emits a new state event to all subscribed 
components, ensuring the UI remains perfectly synchronized without redundant 
network requests.

7.3 Dynamic Routing and Route Guards
The Angular Router maps URLs to specific views. Critical routes are protected 
by custom AuthGuards implementing the CanActivate interface. If an unauthenticated 
user attempts to navigate to /buyer-dashboard, the AuthGuard intercepts the 
navigation, checks for a valid JWT within the auth service, and forcibly redirects 
the user to the /login page if the token is absent or expired.

7.4 Forms and Validation
The application heavily utilizes Angular Reactive Forms for complex user inputs, 
such as the intricate multi-step Checkout process and the multi-field Seller 
Product Addition form. Custom synchronous and asynchronous validators ensure 
emails are formatted correctly, passwords meet complexity requirements, and 
usernames are unique against the backend prior to form submission.

7.5 Buyer Dashboard and Order History
The client-side implements data grids utilizing structural directives (*ngFor, 
*ngIf) to iterate precisely over JSON array payloads returned via Angular's 
HttpClient. The Order History page leverages custom Angular Pipes to parse ISO 
date strings into human-readable local time, and formats raw numeric currency 
values based on local i18n standards.

7.6 Interceptors for Global Request Handling
An AuthInterceptor class injects the JWT into the Authorization header of every 
outgoing HTTP request. An ErrorInterceptor class globally catches 401 
Unauthorized or 403 Forbidden HTTP status codes, automatically purging stale 
local storage tokens and returning the user gracefully to the sign-in modal 
while deploying a UI toast notification.


8. EXTERNAL NOTIFICATION WORKFLOWS
--------------------------------------------------------------------------------
8.1 Twilio SMS OTP Validation
To enhance security, the system utilizes mobile device verification. Upon account 
registration, the Spring Boot backend generates a 6-digit random string, hashes 
it, and dispatches it immediately via the Twilio public API to the user's mobile 
number. The frontend blocks progression until the client inputs the matching 
code to verify ownership of the hardware.

8.2 Email Dispatch System (JavaMailSender)
The application leverages Spring Boot Starter Mail configured with an external 
SMTP relay (e.g., Gmail, SendGrid). 
Key triggers include:
- Order Confirmations: Sending detailed HTML-based email receipts itemizing 
  the purchased products and total cost.
- Shipping Alerts: Dispatching updates when the TrackingDetails table is modified.
- Password Recovery: Creating a secure, single-use URL containing a randomized 
  UUID token, allowing users to safely reset forgotten credentials.


9. SUMMARY AND IMPACT
--------------------------------------------------------------------------------
The RevShop project represents a comprehensive assimilation of modern software 
engineering best practices. By successfully architecting a decoupled system 
relying on Java and Angular, the final product achieves exceptional modularity, 
maintainability, and distinct separation of computational concerns. 

The implementation of robust testing frameworks (JUnit, Karma) guarantees 
long-term stability, while the integration of modern external APIs (Razorpay, 
Twilio) accurately mirrors the complexities of active enterprise environments. 

Through diligent use of ORM data modeling, strict RESTful design patterns, and 
stateless JWT security, RevShop successfully demonstrates the capacity to design, 
develop, and deploy scalable B2B and B2C solutions.
